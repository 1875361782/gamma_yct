# 一窗通填报插件 · 设计说明

目标站点：`https://online.yct.sh.gov.cn/web-yct-master/`（上海市企业登记在线「一窗通」），
入口路由 `?web-name-apply=/web-name-apply/#/name-declaration#/wujieViews/A1`（名称申报）。

本文只讲**为什么这么做**。怎么用见 [README.md](README.md)。

---

## 1. 为什么是浏览器插件，而不是继续用服务端浏览器

仓库里已经有一条服务端路径：`BrowserTaskService` + Selenium（`af_infra/browser/webdriver.py`）。
2026-08-04 晚上的两次排查（commit `8013386`、`a0490fb`）把它逼到了墙角：

> 在活会话里直接调站点的三支字典接口（`dicname/getDistrictDesc`、`getOrgForm`、
> `getIndustryDesc`），全部返回「当前请求已拦截，请登录后再试」，`code=401`；
> 再查会话：**零 cookie、localStorage 零项、无任何令牌**。

也就是说，卡住那一页的不是选择器写得不对，是**没有登录态**。而这个站点的登录要走
随申办实名、扫码或人脸，这些环节按设计就不该由程序代劳。

插件把执行面搬进用户自己的 Chrome：登录态天然存在，登录、实名、人脸、扫码、电子签名
全部由用户本人在同一个浏览器里完成。这不是绕过风控，是把不该自动化的部分交回给人。

同时，`webdriver.py` 里那套已经对着**这一页**调通的 DOM 逻辑（Element Plus 下拉判定、
wrapper 鼠标序列、选项枚举、回读防假阳性）是纯 DOM JavaScript，直接搬进 content script
即可，不必重来一遍。

## 2. 分层

```
manifest.json
└── content_scripts
    ├── MAIN world   src/main-world/net-probe.js     只读接口嗅探（可关）
    └── ISOLATED     common/  namespace policy field-map site-profile
                     content/ roots trusted labels controls selects dialogs
                              page planner runner panel main
background/service-worker.js   留痕落盘 + 可选平台桥 + CDP 可信输入（只开放 Input 域）
ui/                            popup（快捷动作）· options（档案与设置·可信输入开关）
```

职责边界，越界过一次就会出乱子：

| 层 | 只做 | 绝不做 |
| --- | --- | --- |
| `roots` | 收集可遍历的根 | 认识业务语义 |
| `labels` | 标签 / 分区 / 必填 | 碰值 |
| `controls` | 分类、读、写、回读 | 决定填什么 |
| `trusted` | 可信地点下去（坐标换算、遮挡预检、CDP 桥） | 决定点哪里 |
| `selects` | 展开、归属、枚举、择一 | 决定选哪个（只做确定性匹配） |
| `dialogs` | 识别弹窗并分级 | 替人做意思表示 |
| `page` | 观察与指纹 | 改 DOM |
| `planner` | 字段 ↔ 档案 | 碰 DOM |
| `runner` | 编排与闸门 | 认识站点细节 |
| `site-profile` | 站点特征 | 通用逻辑 |

## 3. 六个必须做对的技术问题

### 3.1 wujie 微前端：子应用在 blob: iframe 里，脚本进得去吗

站点用 wujie，子应用挂在 `blob:` iframe，并且用开放 shadow root。
Chrome 是否向 `blob:` 文档注入声明式 content script 并不可靠。

**决定：单实例 + 同源穿透。** 只有顶层 frame 跑引擎，`roots.js` 一次性收集
「顶层文档 → 所有开放 shadow root → 所有**同源** iframe 的 contentDocument」。
`blob:` 继承创建者 origin，所以 `iframe.contentDocument` 一定拿得到。

好处不只是可靠：跨 frame 的消息编排复杂度直接归零，字段标记也不会因为两个实例
各标一遍而互相覆盖。

**代价，写在明处**：跨源 iframe 看不见。本站业务只在 `online.yct.sh.gov.cn` 一个源上，
跳到 `zwdt.sh.gov.cn` 登录时本来就该交还控制权，所以这个代价可接受。真出现跨源业务
frame，要改的是 `roots.js`，不是引擎其他部分。

`all_frames: true` 仍然保留——为的是让 MAIN world 的接口嗅探覆盖到子应用。

### 3.2 什么算「必须从选项里挑」的控件

判据用**容器类名**，不用 ARIA 角色。两条踩过的坑决定了这个选择：

1. Element 的 filterable select 在内层 input 聚焦时会把 `readOnly` 置回 `false`。
   按 `readOnly` 判定，只要那一刻恰好聚焦过，下拉就会被当成普通文本框走 JS 直接赋值——
   值进不了组件的数据模型，而回读读到的正是 JS 刚写进去的那个值，于是**核验假阳性通过**，
   页面随后重渲染把它清空。
2. `el-autocomplete` 的结构是 `<div role="combobox"><input role="textbox">`，它允许自由输入
   （本站「行业表述」正是这种）。把祖先的 `role=combobox` 算进来，就会逼它去匹配一个
   根本不存在的选项。

于是 `controls.kindOf()` 的判定顺序是固定的，`autocomplete` 必须最先判：

```
secret → file → checkbox/radio → SELECT → contenteditable
→ el-autocomplete → el-cascader → el-date-editor → el-select/ant-select
→ 自身 role=combobox / aria-haspopup=listbox
→ readonly && el-popover__reference   （组织形式那类）
→ text
```

最后一条必须要求只读：同样挂着 `el-popover__reference` 的「名称字号」是真正的文本输入框，
误判成选择器就永远填不进去。

### 3.3 选项归属：弹层被传送到 body，和触发它的输入框没有父子关系

政务下拉的选项来自接口，点开才请求、才渲染，而且弹层挂在 `<body>` 底下。
直接「扫全文档取可见选项」会把上一个下拉的残留、以及其它已展开的弹层一起读进来。
`webdriver.py` 的实现就是全文档扫，这是它留下的隐患。

**展开：多策略逐个试，每次试完验证。** 这里踩过两次，两次的教训方向相反：

- 只发 `el.click()` 打不开 Element 的 select——它没有 mousedown，而组件常常听 mousedown；
- 反过来只往 wrapper 直派也不行——**事件不会从祖先向后代传播**。Element 各版本的
  监听点不一样（有的在根 `.el-select`，有的在内层 `.el-input` / `.select-trigger`），
  往最外层派发时，监听在内层的那一版收不到任何东西，表现就是「点了没反应」。

所以第一策略是从**内层控件自身**发出完整指针序列（pointerdown → mousedown →
pointerup → mouseup → click），靠**冒泡向上**同时覆盖两种绑定；够不着时依次升级到
`.select-trigger` / wrapper 直派、再到键盘 `ArrowDown`+`Enter`。每试一种就查一次弹层，
开了就停——**绝不能四种一口气全发**，前一种打开的会被后一种切回关闭。

两段等待是分开的：弹层容器同步渲染，判断「开没开」只等 120/300ms（四种全试完最坏
1.7s）；确认开了之后，再按 400/800/1200 的节奏等接口把选项送回来。

**归属回退**（`selects.resolvePanel`），前三级之外后来又加了一级**按目标文案认领**：
诊断实锤过两个关不掉的弹层同时开着（本站的 el-select 下拉和组织形式 popover 都不吃
Escape 和外部点击），「哪个是新开的」失效，但「哪个里面有我要选的字」依然成立——
要求唯一命中，且要进策略循环内层（触发器多是开关，弹层本来就开着时第一种姿势会把它
切关、第二种再切开，只有每一步都能认领才不被奇偶切换耍了）。

**三级归属回退**（`selects.resolvePanel`）：

1. `aria-controls` / `aria-owns` —— 站点给了就是确定性的；
2. **展开前后差集** —— 展开前记录所有可见选项元素，展开后新出现的必定属于这一个。
   这一级最可靠，也是对 `webdriver.py` 的实质改进；
3. **刚变可见的弹层** —— 组件复用同一个 popper 实例、只替换内容时，选项元素可能是
   同一批 DOM（差集为空），但弹层本身是从隐藏变可见的。

刻意**不**退回「取最后一个可见弹层」：上一个下拉没收干净时，那样会拿着别人的弹层去点选项。
选错一个区划就是一次错误申报，宁可如实报 `no_panel`。

展开等待用 400/800/1200ms 三档，与填写阶段的重试节奏一致，不让两处对「多久算慢」
各有一套判断。枚举完必须收起弹层：留着会遮住后续字段的可见性判定。

**级联（区划、住所）另走一条路。** 第二级起不再调用 `openWidget`——弹层这时已经开着，
再往 wrapper 派发一次 mousedown 会把它收起来，于是永远推进不到第二列。
`chooseCascade` 改为在同一个弹层里取最后一列，并且**要等到列数真的增加**才认为就绪：
下一列的数据来自接口，列数没变就说明还没回来。

选项文案里没有想要的那个时，返回值区分 `empty` / `no_match` / `ambiguous` / `no_panel`
四种，**绝不返回裸 false**——它们在诊断时完全不同，混成一个「失败」会让人查无实据。

**`empty` 和 `no_panel` 必须分得开。** 曾经把「弹层里至少有一个选项元素」当作
「这是一个弹层」的判据，结果显示「无数据」的下拉被判成 `no_panel`——人于是一直去查
「为什么点不开」，而真正该查的是「为什么没数据」。现在空的 `.el-select-dropdown`
本身就算弹层，并且会把弹层里的原话（「无数据」/「加载中」/「请先选择企业类型」）
一并带出来。这句原话通常直接就是下一步该做什么。

**`no_match` 时必须把站点实际给的选项摆到界面上。** 只说「选项里没有这个值」而不摆出
选项，人只能对着「选不中」干瞪眼；摆出来，档案写「有限公司」而站点是「有限责任公司」
这种问题一眼就能改掉。

### 3.3.1 静态提示不是选项，它是「上一步没做」的证据

「组织形式」的弹层里写着 `1. 请选择企业类型` / `2. 请选择组织形式`。这两行长得和选项
一模一样，点它没有任何意义。这段文字已经害过两次：

- 第一次（`a0490fb`）把它误读成「级联前置没满足」，整个排查方向跑偏，真实原因其实是未登录；
- 第二次是这一版：兜底选择器把「2. 请选择组织形式」当成**唯一的选项**报给人，界面上
  出现了「站点实际给的选项：2. 请选择组织形式」这种毫无意义的建议。

现在 `HINT_TEXT`（`^\d+[.、]?\s*请(选择|输入|…)`）把它们从选项里剔掉，但**不丢弃**——
弹层里只剩提示、没有真选项，本身就是「这是分步选择器、上一步还没做」的直接证据。
这一类单独返回 `needs_prior_step`，与「站点没给数据」的 `empty` 分开，因为两者的
下一步完全不同：前者去补上一步，后者去查登录态。

### 3.3.2 分步选择器：级联和向导是同一件事

区划的级联（多列）和组织形式的向导（先选企业类型再选组织形式）在代码里是同一段
`chooseSteps`：在**同一个弹层里**逐级点下去，第二级起不再 `openWidget`（会把弹层收起来）。

「下一级就绪」的判据是**候选集变了**，不是「有候选」——政务弹层的下一级要等接口回来，
不等就点会把上一级的残留当成下一级。判据用元素身份取差集；差集为空时再退回比较文案
集合，因为有些实现复用同一批 DOM 只换文字。

路径怎么来：档案直接给数组时数组优先；否则查 `site.stepPickers` 的声明，按步骤逐个去
档案里取值拼出来。缺某一步的值时**不跳过**——企业类型可能在上一页已经选过，弹层第二级
也许直接可用；跳过等于替站点做了一个我们没资格做的判断。缺口一路带到结果里，真撞上
`needs_prior_step` 时才说「档案里补上 `enterprise.enterprise_type`」。

**容错步进：用户给的路径不必和站点的层级严丝合缝。** 一窗通「组织形式」实测的第一步里
还带一层分组（内资企业 › 有限公司），而分组标题在不同实现里有时可点、有时只是一行字。
与其赌一种，不如让路径宽容：

- 这一级匹配不上、而下一级能对上 → 把这一级当分组标题跳过（记进 `skippedLevels` 报出来）；
- 点完候选一点没变、但要找的就在当前列表里 → 直接继续，不干等到超时；
- 本级「新出现的」候选里没有 → 退回整个弹层再找一次（分组列表、或上下两级共用容器）。

于是 `["内资企业","有限公司","有限责任公司"]` 和 `["有限公司","有限责任公司"]` 都能走通。
放宽的只是**层级对齐**，匹配本身仍是精确/归一化/唯一前缀三级，多个候选照样停下来问人。

### 3.3.3 自动补全：打字只是第一步

`el-autocomplete`（本站「行业表述」）允许自由输入，所以它**不能**按下拉处理——逼它去
匹配一个不存在的选项只会永远失败。但反过来「只把文字写进去」同样是错的：组件的数据
模型要等 `select` 事件才更新，光写 input 的 `value`，**站点收到的是空值**。

这是这套站点最隐蔽的一种假阳性：回读读到的正是 JS 刚写进去的那串字，判定通过，
面板显示 `ok 实测：信息科技`——然后下一步被站点打回来说没选。`stableRead` 也挡不住它，
因为值确实稳定，只是没进组件。

所以 `autocomplete` 走独立分支：`writeText(el, v, { commit: false })` → 等候选渲染 →
从候选里择一点中。两个细节：

- **`commit: false` 不可省。** `writeText` 收尾会派发 blur 并真的失焦，而 blur 正是组件
  收掉候选面板的信号——打完字就 blur，候选还没渲染出来就没了。
- **候选是打字触发的，不能去点控件。** 点一下反而常把候选关掉，所以这里只补一次
  `input` 事件，不走 `openAndResolve` 的那套展开策略。

三种结局分开处理：选中了 → 正常回读；一个候选都没出来 → 这个控件本来就允许自由输入，
补上收尾事件保留文本；**有候选但没有档案里的那个 → 判失败**，把站点候选列出来。
最后这条不能宽容：文本留在框里只会把问题推到下一页。

**它还有两个值，不是一个。** 「打什么字」（查询词）和「选哪一条」（绑定行业代码）是
两回事：候选长成「信息科技 (主营行业:互联网信息服务(07532))」，括号那段只是展示后缀；
把整串打进输入框，站点一个候选都搜不到，还会判非法**清空输入框**并弹
「请输入正确的行业表述！」。把两个值当成一个，就是这一关反复失败的根因。

处理：**查询词从选中项自动推导**（取第一个括号前的部分），依次试「档案显式给的第一段 →
括号前那段 → 整串」，第一个搜出候选的赢；回读按查询词那一侧比对（输入框最终显示的是它）。
档案写整串或写 `[查询词, 选中项]` 两段都认。选中后必须 `blur()`——候选面板赖着不走，
会把下一个字段的展开判成打不开（组织形式那次 `no_panel` 误报正是被它挡的）。
站点清空输入框的情况单独报 `cleared_by_site`，并当场用查询词把候选枚举出来供人点选。

### 3.3.4 自绘弹层：候选靠文本叶子认，同名候选靠分组消歧

一窗通「组织形式」的弹层在登录态下实测长这样：

```
1. 请选择企业类型
   内资企业 › 有限公司 / 股份公司 / 非公司企业法人 / 个人独资企业 / …
   外资企业 › 有限公司 / 股份公司 / …
2. 请选择组织形式
```

它一口气暴露了三个问题：

**① 选项不是 `li`，选择器兜底一个都捞不到。** 这些条目是 `div`，`LOOSE_OPTION_SELECTOR`
（`li, td, .cell, .item, .option, [class*='item']`）全部落空，界面上只剩一条碰巧命中的
「2. 请选择组织形式」，看起来就像「站点没给选项」。政务站点的自绘弹层用什么标签没法穷举，
所以最后一层兜底改成**文本叶子**：可见、自己带文字、没有更深的带文字后代、且不含表单控件。
安全性靠别处保证——真正会被点中的只有文案命中档案值的那一个。

**② 空态那行字会被当成选项。** 换成文本叶子之后，`.el-select-dropdown__empty` 里的
「无数据」立刻变成了一个候选，于是「开了但没数据」被报成「有一个选项叫无数据」，
比不报还糟（自检当场抓到）。空态单独识别并剔除，且**不计入 hints**——
它说明的是「站点没给数据」，与提示行的「上一步没做」指向完全不同的下一步。

**③ 「有限公司」在两个分组下各有一个。** 不按组收窄就只能判歧义然后停下来，
而用户给的路径里本来就写了是哪个组。所以 `chooseSteps` 在歧义时，用**上一级点中的那一项**
当分组标题再收窄一次（`scopeUnderHeader`：父容器 → 文档序到下一个同类元素 → 之后全部）。
第一级就撞歧义（没有上一级可依据）时不硬猜，返回 `groupHint` 提示补上分组名。

后来按用户约定又放宽了一档：**字面完全相同**的重复项取文档序第一个（`chooseOne` 返回
`duplicate` 而非 `ambiguous`，界面明说「已按约定取第一个」）。只对字面相同放宽——
「信息科技 (主营行业:A)」与「…(主营行业:B)」不是重复项，是两个不同的业务选择，照旧判歧义。
优先级：路径里写了分组名 > 分组收窄 > 取第一个。

**路径长短都容错**：比向导浅 → 报 `needs_next_level` 并把下一级候选交出来（面板做成
可点按钮，点一下写回档案并重填）；比向导深 → 多出来的段忽略（`extraLevels`），值填没填上
交给回读判。「下一级就绪」按**元素身份**取差集判断，不能按文案——第二级里有个和第一级
同名的「有限公司」，按文案会把它当成「见过了」漏掉。

同一份数据还印证了自动补全那条：站点候选带 `(主营行业:互联网信息服务(07532))` 这类后缀，
档案只写「信息科技」会同时命中两条。选哪个行业代码是业务决定，判歧义交给人是对的。

### 3.3.6 弹层归属的判据是**几何锚定**，不是「新出现的」

2026-08-06 登录态实测（组织形式）逼出来的一条。当时的现象是：`fill` 报
`blocked_by_stale_panel`，而挡路的弹层内容恰恰是**组织形式自己的**那一个。

链条是这样的：`observe` 阶段枚举选项时把它的弹层打开了，收尾没关掉（本站的
`orgDescPopper` 既不吃 Escape 也不吃合成的外部点击）；轮到 `fill`，
`resolvePanel` 按「只认新出现的弹层」把它排除掉——它在展开前就可见，不算新的。
更糟的是触发器是个**开关**：六种展开姿势轮流去点，弹层在开/关之间摆动，
收尾那一刻正好是关的，于是报「六种全试过还是打不开」。人只会去查「为什么点不开」，
而真正的原因是「它早就开着，是我们自己把它点没的」。

**改成几何锚定**：Element Plus 的 popper 定位在触发器正上/正下方，水平投影必然
重叠。`isAnchoredTo(panel, el)` 把两者都换算到顶层视口坐标（弹层传送到 body 的顶层
文档，触发器常在 blob: iframe 里，不换算根本没法比）再比位置。它同时解决两个方向：

- 自己的 stale 弹层**认得回来**（`already_open` 短路：锚定在本触发器上就直接用，
  绝不再去点那个开关）；
- 别人的弹层**认不进来**——相邻两个区划下拉的候选高度重合，只按文案会认错人。

按文案认领因此分成两档：新出现的弹层只要文案唯一命中就认；本来就开着的，
必须**同时**满足文案命中和几何锚定。

配套还有两处：枚举与探查的收尾改用 `closePanelsHard`（合成关不掉就用一次**可信的
空白处点击**——那是可信通道除了「点得中」之外的第二个价值，收拾合成事件收拾不了的
残局），落点由 `findSafeSpot` 扫出来，避开弹层内部、可交互元素和插件自己的面板。

### 3.3.7 radio 型候选：合成事件点不动它，而且点不动时会**假装成功**

同一天再往里一层。弹层归属修好之后，第一级「内资企业 › 有限公司」确实选中了
（`label.el-radio.is-checked`），第二级也渲染了出来，可回读仍是
`empty_after_write`——组织形式的输入框还是空的。

看 outline 就明白了：第二级那两项都没有 `is-checked`，**它根本没被点上**。而
`chooseSteps` 走完了两级、返回成功。两个原因叠在一起：

1. **第二级在 popover 可滚动区的底部**，可信点击的命中预检判它出了视口、拒绝派发，
   回退到合成事件；
2. **合成的 `dispatchEvent(new MouseEvent('click'))` 不触发默认行为**——点在
   `label.el-radio` 上，里面那个隐藏的 `input` 不会被选中。元素自己的 `.click()`
   方法才会（它走 UA 的激活路径，label 的关联激活会发生，组件也就收到了 change）。

三处修：**滚动**（选项点击前一律 `block:"center"` 并等一帧，贴边会让预检判出界；
可信点击若报 `out_of_viewport`/`occluded`，先滚进来再试一次）、**兜底**（合成路径对
radio/checkbox 补一次 `node.click()`，还不中就直接 `input.click()`）、
**验证**（点完立刻查 `checked`，没中就报 `click_not_applied` 并说清是「点到了但没
生效」）。

第三条最重要，因为最坏的结果不是「没点上」，而是**没点上却报成功**：引擎照常走完，
最后只有回读说一句「值是空的」，人根本看不出是哪一级、为什么没生效。这与「回读核验
是唯一真值」的纪律并不冲突——回读挡的是「写进去又被清空」，而这里挡的是「压根没写
进去却继续往下走」，越早停越好。

### 3.3.8 「第几级」要按站点的结构分，不能按「哪些候选是新出现的」

组织形式的最后一关。前面都修对了——弹层认得回来、radio 认得出、点得中、点不中会
报错——回读却仍然是 `empty_after_write`，而 `click_not_applied` 那道验证**没有触发**。

链条：点完第一级，Element Plus 会**重渲染整个 radio-group**，12 个 label 全部换成新的
DOM 节点。于是「新出现的候选」这个差集判据把**全部 14 项**都算成新的，
`chooseOne("有限公司", …)` 在三个同名项里按约定取第一个——又是第一级那个刚选中的
「有限公司」。验证 `checked` 当然通过（它本来就选中），循环走完、报成功，
而第二级从头到尾没被碰过。

**判据改用站点自己的结构。** 这个弹层的 DOM 里明写着层级：

```
ul
  li > p «1. 请选择企业类型» + 候选     ← 第一级
  li > p «2. 请选择组织形式» + 候选     ← 第二级
```

`stepGroups()` 按「带步骤提示行的祖先块」给候选分组，第 N 级只在第 N 组里找。
两个细节决定成败：

- **只有一组也要返回**，那说明下一级还没渲染出来（候选要等接口），而不是「这不是
  分步结构」。判成后者就会拿上一级去匹配下一级，同名项一撞就点回上一级。
- 分不出组时（区划那种多列级联、或提示行与候选是兄弟的结构）**退回差集法**，
  不硬套。曾经写成「只要弹层里有提示行就等下一级」，结果把「提示行和候选是兄弟」
  的那类结构等到超时，一次打挂 5 条老用例。

**分好级之后，两条兜底必须一起收紧**，否则分组等于白做（对抗性评审在真实浏览器里
复现出来的，两条都踩「绝不能点错选项」这条红线）：

- **目标不在第 N 组时绝不放宽到整个弹层。** 路径 `["有限公司","股份公司"]` 的第二级
  里没有「股份公司」，放宽之后命中的是**第一级**的「股份公司」并点了下去——把已经
  选对的企业类型改掉，组织形式仍然是空，而且返回成功。三条纪律一次踩全：点错了、
  没停下来问人、报了假成功。同理，歧义收窄的底、「下一级能否对上」的判断、以及
  失败时摆给人看的 `available`，都只能用**本级**的候选。
- **分组索引要用「已提交的级数」（`picked.length`），不是路径下标。** 跳过分组标题
  那条路只加 level 不加 picked，两者从此错位：在两组的弹层里去要 `groups[2]`，
  于是白等 4500ms 超时，而目标当时就在第二组里。档案写
  `["内资企业","有限公司","有限责任公司"]`——正是站点档案注释推荐的写法——必踩。

诊断里的 `steps[].from` 要记**真实**来源（放宽过就写 `group1/2→all`）：
出现「`from: group1/2` 而 `poolSize: 9`」这种自相矛盾的记录，比没有记录更误导。

自检的 fixture 必须**照抄真实结构**，这一条在这里被再次证明：R 的 fixture 一开始写成
「提示行和候选是兄弟」，与线上的「同在一个 li 内」不符，于是分组逻辑测不到真问题；
更要命的是它没有复现「点完第一级整组重渲染」，而那正是病根本身。fixture 不真，
用例全绿也说明不了任何事。

### 3.3.5 探查弹层

政务站点的自绘弹层长什么样，猜是猜不出来的——组织形式这一个已经被误读两次。
所以每个下拉那一行都有「探查弹层」按钮：展开它、把容器类名、被识别成选项的、
被识别成提示的、以及整棵 DOM 轮廓原样倒出来。与其继续猜，不如一次性看清。

### 3.4 「上海」怎么对上「上海市」

分两步，分工清晰：

- **枚举**（JS）：先展开下拉，读回站点真实的合法值集；
- **择一**（`util.chooseOne`）：三级，精确 → 归一化 → 唯一前缀。
  归一化刻意做得很浅（全角转半角、去空白、去括号内容），**不做**繁简转换、
  不去「市/省/区」后缀——那会把「浦东新区」和「浦东」判成同一个。
  后缀差异交给第三级「唯一前缀」，且要求**唯一**；匹配到多个是一次歧义，停下来问人。

非精确匹配的结果会在面板上标出来。站点接受了一个与档案不完全相同的写法，
这件事必须让人看见，而不是悄悄通过。

### 3.5 弹窗：确认框和填写框是两件事

站点在「下一步」和「提交」之后都会弹框。混着处理会出现最难查的错：
**弹窗开着，引擎却在盘点背景页的字段**。

两条纪律：

1. 有活动弹窗时，字段盘点、按钮查找一律限定在活动弹窗子树内（`page.snapshot()` 自动
   把 scope 切到活动弹窗）。活动弹窗 = 可见弹窗里 z-index 最高的那个，且**下拉弹层不算弹窗**
   （它们的 z-index 常常更高，混进来引擎会去点选项）。
2. 三级分类（`dialogs.classify`）：

   | 分类 | 判据 | 处理 |
   | --- | --- | --- |
   | `human` | 文案命中人工词表，或按钮里有最终提交措辞 | 停下来交给人 |
   | `fill` | 弹窗里有可填业务字段 | 当独立子表单盘点填写，**填完仍需人确认** |
   | `confirm` | 纯提示 / 步骤确认 | 预算内自动点掉（一页最多 3 个） |

人工词表与后端 `browser_tasks/service.py` 的 `_DIALOG_HUMAN_ONLY` 同源：授权、委托、
承诺、声明、签署、实名、人脸、放弃、注销、支付、法律责任……这些标记的是一次**法律意义上
的意思表示**、一次身份核验，或一次不可撤销的动作。插件替人点掉，等于替人做了它没有资格
做的决定，而事后没有任何办法证明用户本人同意过。

纯确认弹窗里找不到唯一安全的「确定」按钮时，不乱点，交给人。

### 3.6 回读核验：怎么识破「写进去了又被清空」

单次回读挡不住这套站点最常见的失败：JS 直接赋值 → 立刻读到自己写的值 → 判定通过 →
Vue 下一轮渲染按数据模型把它清空。

`controls.stableRead()` 采样两次，中间跨过至少一个渲染周期（`rAF` ×2 + 500ms），
两次一致才算数。不一致直接判 `unstable_readback`，并把「先读到什么、再读变成什么」
如实写进结果。

分类沿用平台口径：`match` / `site_wording`（站点用了不同写法但语义一致）/
`transformed`（站点改写了值，例如金额补零、日期换格式——**不默认通过**，要人确认）/
`empty_after_write` / 各类 `failed`。

### 3.7 执行末端：可信输入优先，合成事件兜底

content script 合成的事件 `isTrusted=false`。本文件反复出现的三类怪病——组件只听
mousedown、点了没反应时灵时不灵、JS 赋值进不了 Vue 数据模型——共同的病根都在这里：
事件没走浏览器的真实输入管线。2025-2026 年的主流浏览器自动化框架（browser-use、
Stagehand、Nanobrowser）在这一点上收敛到了同一个答案：经 CDP 的 Input 域派发输入，
事件 `isTrusted=true`、带完整 pointer/mouse 序列、经过真实 hit-testing，页面无法
区分它和真人。国内 RPA 厂商的等价物是桌面程序的 OS 级键鼠注入，方向相同。

**决定：执行末端换通道，感知层一行不动。** `trusted.js`（content）负责把元素换算成
顶层视口坐标并做遮挡预检；service worker 经 `chrome.debugger` 附着本标签、只发
`Input.*` 命令。「点哪里」仍由 selects/runner 的既有逻辑决定——五级弹层归属、
分步向导、择一匹配全部保留，CDP 只替换「点下去」那一下。

降级梯子（每一次点击都有着落，绝不赌通道状态）：

| 级 | 通道 | 什么时候走 |
| --- | --- | --- |
| 1 | CDP 可信点击 | 权限已授予、通道就绪、预检（视口内、未遮挡）通过 |
| 2 | 合成指针序列（既有 fireMouse/策略梯） | 通道不可用，或可信点击报 occluded/失败 |

七个必须做对的细节（每一条都对应一次评审逮住的真缺陷）：

1. **坐标要逐层加 iframe 偏移，到不了顶层就返回 null。** CDP 的坐标系是顶层视口，
   wujie 子应用在 blob: iframe 里，沿 `frameElement` 链把每层 iframe 的位置和
   `clientLeft/Top`（边框）加上去。链走不通、或嵌套深到走满上限时**必须返回 null**：
   带着只累加了一半的坐标去点，等于点在完全无关的位置。
2. **遮挡预检必须逐层查到顶层。** CDP 点击走真实 hit-testing，被弹层/遮罩/面板盖住
   时点到的就是盖着的东西。只在元素自己的文档里 `elementFromPoint` 是个盲区——目标
   在子应用 iframe 里、遮罩在顶层文档时，子文档查得好好的，而这一下真实点击落在顶层
   遮罩上（遮罩上的点击在某些站点等同于「取消」），偏偏还会被报成成功、调用方不回退。
   所以每上升一层，都要在该层文档里确认这个点落在承载下一层的那个 iframe 上。
3. **缩放要么补偿要么不点。** 页面级缩放（Ctrl +/−）在后台用 `chrome.tabs.getZoom`
   乘回去；捏合缩放（`visualViewport.scale ≠ 1`）拿不到可靠因子，直接拒绝走合成——
   坐标差几十像素就会点到隔壁选项上，而选错一个区划就是一次错误申报。
4. **降级要分「永久」和「瞬时」。** 权限没给、设置里停用、用户点掉横幅、被 DevTools
   占用，这些在本页内不会自己好转，撞上一次就整页降级，不再每次点击都白试；attach
   竞态之类的瞬时失败只报本次。特别地，「already attached」探测里只有明确的
   `not attached` 才判定为别人的会话——一次瞬时失败不该让整页永久丢掉可信通道。
5. **用户点掉横幅 = 收回授权，不得自动重连。** 三个地方都要守住：入口查否决、
   重试分支再查一次（在途命令失败与点掉横幅是同一时刻发生的）、attach 成功后还要
   复查（attach 与 onDetach 有竞态，连上了就主动松开）。否决记号落
   `chrome.storage.session` 而不是内存——SW 闲置回收会把内存记号清零，那样横幅会在
   用户什么都没做的情况下自己弹回来。
6. **序列发到一半绝不重放，也绝不补合成点击。** 一次点击是 mouseMoved→mousePressed
   →mouseReleased 三条命令。会话半路断掉时，在途命令报的「Detached while handling
   command.」分不清是「一条都没发」还是「发到一半」。整段重放已经落地了 mousePressed
   的序列，页面会收到两次 mousedown——Element 下拉是开关，等于点开又点关。所以后台
   按**已落地**的条数计数（自增写在 await 之后，写在前面的话第一条命令失败也会被算成
   已落地，「可以安全重放」这条路就永远进不去），落地过就如实报 `interrupted`。

   `interrupted` 是「可信失败必须回退合成」这条纪律**唯一的例外**：这时补一整套合成
   序列，页面就收到了第二次 mousedown，比不补更糟。所以**五个**调用方收到它都不再补
   事件——选项点击、勾选、按钮三处直接返回，展开梯子的两级（可信点击、可信键盘）则
   停止继续试后面的姿势（触发器是开关，换个姿势再点一次同样会切回去）。这一下到底成
   没成，交给本来就存在的验证：展开路径每步查弹层、选项路径判候选集变化、字段路径
   `stableRead` 回读、翻页路径等页面指纹变化。没有这条例外，后台不重放也是白费。

   两个配套的坑，都是评审逐个逮出来的：**分类必须只有一份**。「序列半途中断」在后台有
   三个落点（正常路径、already-attached 探测、重放的 catch），各写各的必然漂移——前两轮
   就是只改对了一处，另外两处照旧返回 `command_failed` / `attach_failed`，content 侧不认，
   照样补点。现在统一走 `classifyRunError`。另外**否决不能覆盖 reason**：用户点掉横幅
   与命令在途失败是同一时刻发生的，把 `user_detached` 写进 reason 会把「已落地」这个
   事实冲掉，所以否决单独用一个 `veto` 字段带回，降级和免补点两件事各归各。
7. **onDetach 必须幂等注册，不能只在 SW 顶层注册一次。** `debugger` 是可选权限：
   SW 在未授权时启动的话，`chrome.debugger` 命名空间还不存在，监听就永远缺席；而用户
   随后在设置页授权、命名空间热挂上来（CDP 会话又让这个 SW 一直活着），此时点掉横幅
   没有任何人记否决 → 下一条命令报 not attached → 自动重连，横幅点掉就回来。所以每次
   attach 前补注册一次，并监听 `permissions.onAdded`。

同理，「勾选」的合成兜底补点必须**按目标状态**判断而不是按「还没勾上」：档案要求取消
勾选时，第一击成功取消之后「还没勾上」恰好成立，补点又把它勾回去，净效果为零——
这个字段于是永远填不成「否」，而回读只能报「没填上」。

还有两条同源的纪律，都是「换了可信通道之后，原本无害的写法开始真的生效」：

- **可信键盘只发 ArrowDown，不发 Enter。** 合成 keyboard 策略里一直带着 Enter，
  没出过事是因为合成事件常被组件忽略。换成可信事件后它会真的生效：展开的同时把列表
  第一项**选中**，而回读读到的正是这个错值——这是最坏的一类失败（看起来成功了）。
  展开就只做展开，选哪个是 `chooseOne` 三级匹配的事。
- **按文案认领弹层要分场合。** 展开循环内只认「新出现的」弹层；本来就开着的那个，
  只有四种展开姿势都试完、确定不会再新开弹层时才允许认领。相邻两个区划下拉的候选高度
  重合，循环内就放开认领的话，本控件弹层还没渲染出来的那 120ms 里会认领到上一个字段
  留下的弹层，于是在**别人的弹层**上点选项——本字段回读会报没填上，而被误点的那个
  字段已经被悄悄改掉，回读体系根本覆盖不到这次跨字段误伤。

代价，写在明处：

- 附着期间页面顶部有「正在调试此浏览器」横幅。**不隐藏、不绕过**——attended 场景
  下它就是这个通道的透明性声明，用户点掉即收回控制权。附着刻意做在通道就绪那一刻
  （而不是第一次点击时）：横幅会挤掉几十像素高的视口，这一次回流必须发生在任何
  坐标换算之前，否则第一击就是「按旧布局算、按新布局点」。
- 设置页「停用」必须**先松开再收权限**：权限一收回，`chrome.debugger` 命名空间就没
  了，detach 再也发不出去，横幅会一直挂到用户关掉标签页。
- `debugger` 是敏感权限，而且**不能做可选权限**——Chrome 把它列在「不允许出现在
  `optional_permissions` 里」的名单上。曾经按平台地址那套（`optional_*` + 用户手势
  申请）写过一版，实测报 `Only permissions specified in the manifest may be
  requested.`，开关根本点不动。它只能写进 manifest 的 `permissions`，随扩展安装
  一次性授予，安装时的权限提示因此躲不掉，商店审核也会更严。
  于是设置页那个开关是**软开关**：只写 storage 标记，不申请也不收回权限。强制力
  由两道保证（都不依赖权限本身）——后台 `withCdp` 每次派发前查 `trustedInput`，
  content 侧监听 storage 变更当场停用；停用还会先把所有已附着标签松开。
  要彻底收回权限，只能在 `chrome://extensions` 里停用或删除扩展，界面上照实说明。
- 每标签同时只能有一个调试方，与用户自开的 DevTools 互斥。
- 后台**只开放 Input 域**。不碰 Runtime/Page/DOM——这个通道拿到的能力必须和
  「一只手」一样多，一点不多；这与 policy.js「不执行任何远程下发的 JavaScript」同源。

**尚未在登录态下实证**（这是全方案唯一未验证的承重假设，首次实跑的第一件事）：
CDP 点击能否在真实一窗通页面驱动 el-select 展开、级联推进、传送弹层选项点选。
自检页能验证的只有坐标换算（含跨 iframe 偏移）、遮挡预检（含顶层遮罩盖住子 frame）、
勾选方向、弹层归属守卫与整条降级路径；**后台那半边（会话管理、否决持久化、
序列中断分类、缩放补偿）在自检页里跑不了**——那些需要真实的 `chrome.debugger`。
真实站点上组件到底吃不吃这套事件，要用「只识别」+ 诊断导出里的 `trustedInput`
（`mode` / `clicks` / `fallbacks`）核对。不吃的话，合成事件路径原样兜底，
行为与本次改造之前完全一致。

顺带修掉的一个**存量致命缺陷**（不属于本次改造，但被它暴露）：`el instanceof Element`
在跨文档时恒为 false。引擎靠同源穿透进 blob: iframe 取元素，而本站业务字段几乎都在
wujie 子应用里——用 instanceof 判定的话，`visible` 全判不可见、`kindOf` 全判 unknown，
`page.inventory` 把子应用的每个字段都跳过，界面显示「当前业务页面没有可填写字段」，
而字段就在眼前。现在统一用 `util.isElement`（看 `nodeType`，跨文档安全），
`roots.inShadow` 同理改看 `nodeType === 11 && host`，`writeText` 的原生 setter 也改从
元素自己文档的构造器上取。顶层 fixture 永远测不出这一条，自检页为此专门加了一条
跨 iframe 的端到端用例。

### 3.5.1 「知情确认」与「法律意思表示」必须分开

实测原话：「您选择申报的为有限责任公司名称，请仔细核对投资人信息，**一经申报无法
修改企业类型**」。它出现在名称申报的「下一步」之后，不点就走不下去。

一开始这个框被当成纯提示自动点掉了（词表里只有「不可撤销」，措辞对不上）。发现后
第一反应是把它归进「永不自动」，结果是**每翻一页都要人点一次，连续填报退化成手动**。
两种做法都不对，因为它们把两类不同的东西混成了一类：

| | 例子 | 性质 | 能否授权代点 |
| --- | --- | --- | --- |
| **知情确认** | 「一经申报无法修改企业类型」「请仔细核对」 | 站点在**告知后果**，等你点头知悉 | 可以——但要先让人读到原话 |
| **法律意思表示** | 承诺书、电子签名、实名/人脸、支付、放弃/注销 | **你本人在做出承诺、表明身份或处置财产** | 不能，任何开关都不放行 |

所以分成两条规则：`HUMAN_ONLY`（永不自动，没有开关）与 `ACKNOWLEDGE`（默认停下，
可授权）。两者同时命中时**一律按更严的处理**——降级路径不能被绕过，自检里有专门
一条守这个。

知情类的默认行为仍是停下来，并把**站点原话**摆在面板上——知情权就是这类提示存在的
全部意义。人读过之后可以点「我已读过，本次运行内代我确认同类提示」：授权跟着本次
运行走，重置即失效，每一次代点都留痕并记下原话（事后要能说清插件替人确认了什么）。

措辞穷举不完，所以认句式：「一经/一旦…无法/不能」「无法修改/不可更改」。

### 3.5.2 「翻过去了吗」不能用页面指纹回答

同一天的另一个坑，代价是**冲掉已经填好的值**。

连续填报的流程是「填一页 → 核验 → 翻页 → 再填」。判断「翻过去了吗」原本用页面指纹，
而指纹回答的是**「DOM 动了吗」**——站点在「下一步」之后弹了个提示框，DOM 一变、
指纹跟着变，就被当成「进入了新步骤」，于是在同一页上又从头填了一遍：名称字号被重写
时被站点清空，组织形式的弹层状态也已不是初始态，跟着 `no_match`。

改用**页面身份** = `stage.id` + 字段标签集合。两个判据回答的是不同的问题，混用必出事。

身份的计算有两个必须避开的陷阱，两个都是实测踩出来的，代价都是**重填一遍、把已经
填好的值冲掉**：

1. **弹层里的字段不算数。** 组织形式那个 popover 一开，弹层里十几个 radio 就被盘进
   字段清单（7 → 19），关掉又变回 7——身份跟着抖，「原地未动」就被判成「进了新页」。
2. **认控件标记，不认标签文本。** 名称申报页那三个拼音选项的标签是**动态生成的名称
   预览**：字号填了叫「上海愿力成像信息科技」，字号被站点清空就变成「上海」。拿标签
   当身份，页面明明没动、身份却变了，于是又一次「以为翻页成功」。改用引擎自己打的
   `data-afy-field` 标记——它跟着元素走，页面没换它就不变。

还有一条同源的：**已填页记录必须跨调用保留**（放在运行状态里）。连续填报会因为
「等你确认一个提示」中途返回，人确认完再点一次继续——记录若随函数局部变量清零，
同一页就会被重填。同时要有并发锁：连点两次、或「授权后自动继续」与手动点击撞在一起
时，两条链会交错着填同一页，比不填还糟。

这三条自检里各有一条用例守着。

还有两条是「翻页」这件事本身的：

- **翻完页要等页面稳下来再进入下一轮。** 弹窗淡入、下一页异步渲染都需要时间；
  紧接着取快照拿到的是半旧状态——弹窗还没被识别到、字段还是上一页的，于是被
  **自己的防重填规则**判成「原地打转」。实测正是这样：明明已经翻到备用字号弹窗，
  面板却说「页面还是同一步」。
- **「下一步」不在可点清单里，要分清是「没有」还是「被禁用」。** `actions` 只收
  可见且未禁用的按钮，两种情况在诊断里长得一模一样，而下一步完全不同：站点在做
  名称查重之类的异步校验时会把按钮暂时禁用，**等它恢复再点就行**（连续填报会等
  最多 15 秒），而按钮真的不在则说明页面已经变了。`inactiveActions` 专门记这个。

### 3.5.3 填写型弹窗要不要替人往下走

备用字号那个弹窗（非必填的两个备选名称 + 「返回修改 / 继续申请」）填完之后，原先
一律停下来等人点。全流程跑下来，这一步每次都要人工介入，与「连续填报」的意义相冲突。

改为：**三个条件同时满足才自动推进**——每一条字段都回读通过（有一条没写进去就不
推进，那等于把问题带到下一页）、找得到唯一的推进按钮（`isDialogProceed`，且不是
最终提交）、用户在设置页授权过。任一不满足就仍旧停下来，并说清是哪一种。

推进按钮单列一套措辞（`DIALOG_PROCEED`）：弹窗里写的是「继续申请」，而页面级的
`NEXT` 只认「下一步/继续」这类，认不出它。这套措辞**刻意排除终局动作**——
「提交/提交申报/完成申报」再像「继续」也走 `FINAL_SUBMIT` 那条要人连点两次授权的路。

`advance` 现在也用同一个判据：发现还在同一页且有弹窗挡着，先把弹窗处理掉再看是否
真的推进；仍在原地就如实报失败，并把**站点那句原话**带出来——它往往直接就是下一步
该做什么。

顺带一条同源纪律：**自动点掉任何确认框之前，先把它的正文记进留痕**。分类可能判错，
但证据不能丢。上面那句「一经申报无法修改」正是靠这条才被看见的——在此之前留痕里
只有标题「提示」和按钮名「确定」，人根本无从知道站点说了什么。

## 4. 安全模型

**插件绝不做的事**（`policy.js` 是这些规则的唯一定义处）：

- 不读、不写、不记录密码、验证码、短信码、一次性口令。识别到直接跳过。
- 不代做实名认证、人脸识别、扫码授权、银行卡核验、电子签名。
- 不勾选承诺书、声明、告知书一类的法律意思表示（`policy.isDeclaration`）。
- 不在 `site.businessOrigins` 之外的任何页面上动作（每个动作入口都先过 `guardOrigin`）。
- 不执行任何远程下发的 JavaScript。声明式动作只有填写、选择、勾选、点击几种。

**最终提交的三道闸**：

1. 本次运行未提交过（`state.submitAttempted`，重置才清）；
2. 用户在面板上**连点两次**「复核并提交」——第一次只展示识别到的提交按钮并要求核对；
3. 点击前的页面指纹与授权时一致，不一致就要求重新复核。

提交后只认页面上的成功文字或办件编号；读不到就交给人目视核对，**不重试**。
重试一次申报比不重试危险得多。面板会明说「已提交」不等于「已核准」，也不等于「已领照」。

**留痕**（`runner.record`）只记状态、来源键路径、失败原因，**不记业务值**——
留痕不该变成一份档案副本。

**接口嗅探**（`net-probe.js`，MAIN world）只观察不改写：只取 URL 的 path（丢掉可能带令牌
的 query）、HTTP 状态、响应体前 400 字里是否出现「请登录」措辞。不读 `data`，不读任何业务值。
它存在的唯一理由是把「下拉是空的」准确地解释成**未登录**而不是级联前置——分不清这两者，
人会顺着错误的方向查很久（已经发生过一次：把组织形式的静态提示浮层误读成级联前置）。

## 5. 数据词汇：为什么是两套路径

仓库里已经有两套企业档案词汇：

- 平台运行面 `enterprise_registration.v1`（`factory-server/domain/af_caseengine/dossier.py`）：
  `enterprise.name.industry_expression`、`shareholders[]`、`personnel[]`、`contact.*`。
  这是 `form_schemas` 和 `/agent/binding-options` 实际下发的那一套。
- 技能包 `field-mapping.md` 的模型侧词汇：`enterprise.name.industry`、`investors[]`、
  `people[]`、`domicile.*`、`capital.*`。更细，是给大模型读的。

插件**取平台那套当主键，技能词汇进 `alt` 回退**，档案按哪一套写都读得到。
接平台后，平台下发的别名前置覆盖内置表——别名的定义权在平台的表单结构，
扩展只做匹配、不做定义。这条纪律在 `.claude` 记忆里有明确记载（此前三份硬编码副本
已经被删过一次），不能又造出第四套。

## 6. 装上就能跑：几个必须做对的工程细节

这些不影响「设计」，但每一条做错都会让扩展装上之后**默默地什么也不做**——
最难查的那类故障。它们都有自检页上的用例盯着（`src/ui/selftest.html`）。

1. **补丁过的 `fetch` 必须带 this 兜底。** `net-probe.js` 里写成
   `originalFetch.apply(this, arguments)` 时，站点严格模式下的裸 `fetch(url)` 调用
   拿到的 `this` 是 `undefined`，Chrome 直接抛 `Illegal invocation`——扩展一装上，
   整个站点就打不开。必须是 `this || window`。自检页有一条用例专门盯它。
2. **`requestAnimationFrame` 在后台标签页不触发。** `stableRead` 依赖它跨一个渲染
   周期，纯 rAF 的实现会让用户切走一下就把整轮填写永远挂住，而且没有任何报错。
   `util.nextFrame` 现在带 250ms 兜底。这个坑是自检页第一次运行时暴露的。
3. **面板样式走 `adoptedStyleSheets`。** 插进页面文档的 `<style>` 要受站点 CSP 的
   `style-src` 约束，政务站点常常没有 `unsafe-inline`，那样面板会变成一堆裸文字。
   构造式样式表不受页面 CSP 管，失败才回退 `<style>`。
4. **平台地址要走 `optional_host_permissions`。** MV3 里 service worker 的 fetch 同样
   受主机权限约束，而平台地址是运行时才知道的，写不进 `host_permissions`。
   权限申请必须发生在选项页的用户点击里（`chrome.permissions.request` 要用户手势）。
5. **模块缺失要喊出来。** 每个模块自带 `if (!AFY || AFY.x) return;` 守卫，任何一个
   文件挂了后面全部静默不装载。`main.js` 启动时点名检查一遍，缺谁直接打进控制台。
6. **面板默认收起。** 420px 压在页面右侧会挡住站点自己的按钮。装上就霸屏是不礼貌的，
   展开与否由用户决定并记住选择。

## 7. 已知限制与待办

1. **重复子表单的行号靠标签出现序号推断**（`labels.occurrenceOf`）。同一页有两个「姓名」
   时，第一个映射到 `personnel[0].name`。这对「先增行再逐行填」的交互是对的，对乱序
   增删行的场景不可靠。更稳的做法是识别行容器再按容器分组，属于下一步。
2. **档案不从平台拉**。现有 `/agent/jobs/next` 下发的是**录制步骤**，不是企业档案。
   要真正跑通「接平台自动取档案」，后端需在 job payload 里带上 `case_data`。
   在那之前，接平台模式下档案仍然来自本地导入——文档和界面上都这么写着，没有装作已完成。
3. **材料上传不代劳**。`File` 只能来自用户手势或已校验的字节流，本地模式没有材料下发通道，
   所以文件类字段一律标为「需你本人选择文件」。
4. **经营范围的目录弹窗**尚未特殊处理。它是「可搜索目录 + 自由文本」的复合交互，
   当前按普通 `fill` 类弹窗处理，填完交给人确认。
5. **`site.stepPickers` 里目前只登记了「组织形式」一项，而且它的第一步用的是
   `enterprise.enterprise_type`。** 万一站点弹层第一级的文案与页面「企业类型」字段
   不是同一套（例如弹层写「内资公司」而字段写「有限责任公司」），这份声明就拼不出
   正确路径——此时把 `organization_form` 直接写成路径数组即可，数组优先于声明。
   弹层第一级到底有哪些值，用面板上的「探查弹层」看一眼最快。
5. **未在登录态下实测**。开发环境无法登录该站点，所有 DOM 假设来自 `webdriver.py`
   对同一页面的实测记录与技能包 references。自检页验证的是「引擎按 Element Plus 的
   典型结构工作」，不是「一窗通当前的 DOM 就长这样」。首次实跑请先用「只识别」核对
   面板给出的字段清单与选项枚举结果，再点「按档案填写」。
6. **没有图标**。`manifest.json` 未声明 `icons`，Chrome 会用默认的拼图图标。
   不影响功能，要换的话补 16/32/48/128 的 PNG 再加 `icons` 字段。
