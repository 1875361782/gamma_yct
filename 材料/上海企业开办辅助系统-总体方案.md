## 1. 背景与目标

### 1.1 业务背景

用户需在上海企业登记在线完成企业设立申报。官方站点**无对外开放的开办 API**，办理路径为：一网通办实名登录 → 网页填报 → 提交 → 相关人员电子签名。

本系统不替代官方站点，而是提供：

1. **分步表单向导**：结构化收集开办所需信息并核验；
2. **受控浏览器自动化**：在客户本人扫码登录后的会话中，自动将已收集信息填入 yct 并提交；
3. **进度反馈**：将页面状态结构化回传给用户，直至进入「待电子签名」。

### 1.2 产品目标（MVP）

| 目标 | 说明 |
|------|------|
| 终点 | 申报提交成功，办件进入**待电子签名**（`awaiting_esign`） |
| 不做 | 代客户完成电子签名、出照、代领材料 |
| 体验 | 用户主要在本系统完成信息确认与扫码；无需在 yct 上手动逐项填表 |

### 1.3 明确不做的事

- 伪造一网通办 OAuth「登录后跳回业务站」拿登录态（无白名单 `redirect_uri` 时不可行）
- 共用一个政务账号、跨客户复用 Cookie
- 承诺无人值守全自动出照
- 个体户、外资、分公司、涉及前置审批等路径（MVP 排除）
- 生产环境用 Cursor / Chrome MCP 跑客户单（仅用于研发探页）

## 2. 已锁定的业务边界

| # | 决策项 | 定稿 |
|---|--------|------|
| 1 | 办事主体 | **客户本人网办**（非代办账号池） |
| 2 | 主体类型 | **仅企业**；MVP 建议收窄为：**内资有限责任公司** |
| 3 | 前置审批 | **仅「不涉及前置审批事项」** |
| 4 | 交付终点 | **提交至待电子签名** |
| 5 | 运行位置 | **我方服务器**上的 Playwright Worker |
| 6 | 登录方式 | **扫码登录**（一网通办 / 随申办） |
| 7 | 并发 | **不考虑并发**；同时最多处理 1 个自动化任务即可 |
| 8 | 账号策略 | **一单一会话**，不共用账号 |
| 9 | 住所 | **地址不唯一**：支持集中登记地与普通住所（租赁/自有等） |
| 10 | 信息收集 UI | **分步表单向导**（非开放闲聊 Agent） |

## 3. 总体逻辑（一句话）

> 用户在本系统用分步向导填好并校验开办数据 → 点击开始办理 → Worker 打开政务登录页并展示二维码 → 用户扫码后登录态留在服务器浏览器会话中 → Worker 按 Playbook 自动填报并提交 → 系统返回「待签名」及办件信息 → 用户自行完成电子签名。

```text
分步收集 → 全量校验 → 扫码登录（会话在 Worker）→ 自动填报提交 → 待签名（人签）
```

## 4. 系统框架

### 4.1 逻辑分层

```text
┌─────────────────────────────────────────────────────────────┐
│  L1 表现层（Web）                                              │
│  分步表单向导 · 确认页 · 扫码/进度页 · 待签名指引               │
└──────────────────────────────┬──────────────────────────────┘
                               │ HTTPS
┌──────────────────────────────▼──────────────────────────────┐
│  L2 业务层（API）                                              │
│  Case 办件 · Payload 校验 · 状态机 · 任务调度 · 文件存储       │
└──────────────────────────────┬──────────────────────────────┘
                               │ 内网/本机队列（单 Worker）
┌──────────────────────────────▼──────────────────────────────┐
│  L3 自动化底座（Worker）                                       │
│  Playwright BrowserContext · Playbook · 截图/二维码 · 结果解析 │
└──────────────────────────────┬──────────────────────────────┘
                               │ 真实网页 HTTPS
┌──────────────────────────────▼──────────────────────────────┐
│  L4 目标系统                                                   │
│  yct.sh.gov.cn · 一网通办登录 ·（签名在用户手机侧完成）         │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 与「假 API」的区别

| 方式 | 本方案 |
|------|--------|
| 官方 REST | **不存在**，不封装假接口伪装成官方 API |
| 真实操作 | Playbook 驱动浏览器操作真实页面 |
| 对外契约 | 业务系统只认统一 Task/Case 状态 + 结构化 `result` |

### 4.3 推荐模块划分（逻辑目录，尚未建仓）

```text
gamma-yct/
  apps/web/                 # 分步向导 + 进度页
  apps/api/                 # Case / 校验 / 调度 / 二维码与截图访问
  apps/worker/              # Playwright + playbooks/
  packages/schema/          # 共用 JSON Schema / 类型定义
  data/
    cases/                  # 办件元数据（或改用 DB）
    uploads/                # 用户上传证件
    screenshots/            # 自动化留痕
  docs/
    fields.md               # 对照 yct 的字段勘探表
    playbooks.md            # 各 flow 步骤与选择器说明
  docker-compose.yml
```

### 4.4 技术选型建议

| 层 | 建议 | 说明 |
|----|------|------|
| Web | Next.js 或 Vue3 | 多步表单 + 进度轮询即可 |
| API | FastAPI（Python）或 Node | 与滑块工具同语言时优先 Python |
| Worker | Playwright（推荐） | 生产主路径；比 Selenium 更适合现代页 |
| 滑块兜底 | 现有 `破盾工具`（可选） | 扫码为主；账号密码+滑块非主路径 |
| 存储 | SQLite/Postgres + 本地文件 | 无并发场景足够 |
| 部署 | 单台 ECS + Docker Compose | web / api / worker |

```text
 │                      │                      │                   │                    │
 │  分步填写 1～9        │                      │                   │                    │
 │─────────────────────>│  PATCH payload       │                   │                    │
 │                      │─────────────────────>│                   │                    │
 │  第9步确认提交        │                      │                   │                    │
 │─────────────────────>│  POST validate       │                   │                    │
 │                      │─────────────────────>│                   │                    │
 │                      │  POST start          │                   │                    │
 │                      │─────────────────────>│  派发 qr_login    │                    │
 │                      │                      │──────────────────>│  打开登录页         │
 │                      │                      │                   │───────────────────>│
 │                      │  awaiting_qr_login   │  二维码截图        │                    │
 │  展示二维码           │<─────────────────────│<──────────────────│                    │
 │  手机扫码            │                      │                   │                    │
 │─────────────────────────────────────────────────────────────────────────────────────>│
 │                      │  轮询 GET case       │  检测登录成功      │                    │
 │                      │<─────────────────────│<──────────────────│                    │
 │                      │                      │  顺序执行 Playbook │  填报/提交         │
 │  进度文案更新         │<─────────────────────│<──────────────────│───────────────────>│
 │                      │                      │                   │                    │
 │  awaiting_esign      │                      │                   │                    │

 │  （用户自行签名）     │                      │                   │                    │
```

### 5.2 用户侧阶段

1. **填写**：分步向导收集信息、上传材料  
2. **确认**：摘要预览 + 全量校验  
3. **登录**：进度页展示二维码，手机扫码  
4. **等待自动办理**：名称比对、填表、提交（可展示当前步骤文案）  
5. **待签名**：系统提示办件号与签名入口指引；**签名在官方侧由人完成**

## 6. 办件状态机

### 6.1 状态一览

| 状态 | 类型 | 含义 | 前端表现 |
|------|------|------|----------|
| `draft` | 中态 | 向导填写中 | 表单步骤 |
| `ready_to_submit` | 中态 | 校验通过，待用户点开始 | 确认页可提交 |
| `awaiting_qr_login` | 中态 | 已出二维码，等扫码 | 展示二维码（可刷新） |
| `logging_in` | 中态 | 可选：检测到扫码中间态 | 「登录中」 |
| `logged_in` | 中态 | 登录成功，即将填报 | 「已登录，开始办理」 |
| `name_checking` | 中态 | 名称自主申报中 | 「名称核验中」 |
| `name_failed` | 可恢复终态/中态 | 名称未通过 | 回到名称步骤改字号/备选 |
| `filling_establishment` | 中态 | 填设立主体信息 | 「填写设立信息」 |
| `choosing_process` | 中态 | 选择办理方式（非集中登记地等） | 「确认办理方式」 |
| `filling_addons` | 中态 | 印章/税务/社保等 | 「填写开办配套」 |
| `submitting` | 中态 | 最终提交 | 「提交中」 |
| `awaiting_esign` | **MVP 成功终态** | 已提交，待电子签名 | 签名指引页 |
| `offline_required` | 终态 | 系统判定须线下/材料辅导 | 说明原因 + 截图 |
| `failed` | 终态 | 明确失败 | 原因 + 截图 |
| `need_human` | 中断态 | 未知弹窗/无法判定 | 人工查看截图后再决定 |
| `cancelled` | 终态 | 用户或系统取消 | — |

### 6.2 合法迁移（简图）

```text
draft → ready_to_submit → awaiting_qr_login → logged_in
        → name_checking → filling_establishment → choosing_process
        → filling_addons → submitting → awaiting_esign

name_checking → name_failed →（改 payload 后）→ name_checking
任意自动化步 → failed | need_human | offline_required
任意非终态 → cancelled
```

### 6.3 统一反馈契约

每次查询办件或任务时，对外固定字段：

```json
{
  "caseId": "GM202608040001",
  "status": "awaiting_esign",
  "customerMessage": "申报已提交，请完成电子签名",
  "currentStep": 9,
  "result": {
    "approvedName": "上海某某科技有限公司",
    "applicationNo": "可选，若页面有办件号"
  },
  "artifacts": {
    "qrImageUrl": "/api/cases/.../qr.png",
    "screenshots": ["/api/cases/.../screenshots/xxx.png"]
  },
  "updatedAt": "2026-08-04T14:00:00+08:00"
}
```

**规则：**

- 成败优先用 **DOM / 固定文案** 判定，不单独靠 LLM 猜。  
- 无法判定 → `need_human`，**禁止伪报成功**。  
- 所有 `failed` / `offline_required` 必须带可读 `reason`（页面原文或摘要）+ 截图。

## 7. 分步表单向导设计

### 7.1 步骤列表

| Step | 名称 | 主要字段 | 局部校验要点 |
|------|------|----------|--------------|
| 1 | 主体与路径 | 企业类型、是否前置审批 | 仅允许有限公司 + 无前置 |
| 2 | 企业名称 | 行政区划、字号、行业特点、组织形式；备选 1～2 | 必填段齐全；禁用词提示（可后期加强） |
| 3 | 住所与登记机关 | 区、详细地址、住所类型、是否集中登记地、意向机关/受理点、住所证明 | 非集中 → 证明材料必传 |
| 4 | 出资与股东 | 注册资本、币种、股东列表、出资额/比例/方式 | 比例合计 100%；金额合计一致 |
| 5 | 人员任职 | 法定代表人、董监高、经理、财务负责人等 | 任职与股东规则、证件号格式 |
| 6 | 经营范围 | 范围文本 / 勾选编码 | 非空；敏感项警告（不阻断或可配置） |
| 7 | 开办配套 | 实物印章、税务发票、就业参保、公积金、银行预约 | 按勾选展开子表单 |
| 8 | 证件上传 | 身份证人像/国徽面等；按角色收集 | 格式 jpg/jpeg、大小限制与官方一致 |
| 9 | 确认提交 | 只读摘要 + 全量校验结果 | 通过才可 `start` |

### 7.2 交互原则

- 支持上一步回退修改；已进入自动化且 Context 仍存活时，**名称驳回优先只回 Step 2**。  
- 每步保存草稿（`draft`），刷新不丢。  
- 文案以说明性固定文案为主，**不依赖 LLM 才能填完**。  
- Step 9 展示风险提示：本人扫码、信息真实性、签名仍需相关人员自行完成。

### 7.3 与自动化的衔接点

| 向导事件 | 系统行为 |
|----------|----------|
| 保存任一步 | `PATCH payload`，状态保持 `draft` |
| Step 9 点「校验」 | `POST validate` → 通过则 `ready_to_submit` |
| 点「开始办理」 | `POST start` → Worker `qr_login` |
| 名称失败 | 状态 `name_failed`，前端打开 Step 2，改完后继续核名任务 |
| 到达待签名 | 展示签名操作指引（随申办 / 登记在线「电子签名」） |

## 9. 自动化 Playbook 框架

### 9.1 执行原则

- 每一办件一个 **BrowserContext**；成功或失败结束后销毁，Cookie 不留给下一单。  
- Playbook 由有序步骤组成：`goto` / `click` / `fill` / `select` / `upload` / `wait` / `assert_text` / `screenshot`。  
- 选择器外置配置，支持 fallback；Playbook 带 `playbookVersion`。  
- 单任务建议超时上限（如 10～20 分钟），可配置。

### 9.2 MVP Playbook 清单

| 顺序 | flowId | 输入 | 成功标准 | 失败/分支 |
|------|--------|------|----------|-----------|
| 1 | `qr_login` | 无（打开登录页） | 检测到已登录 | 二维码过期则刷新；长时间未扫码可超时 |
| 2 | `enter_establishment` | 无 | 进入开办且选中「不涉及前置」 | 入口改版 → `need_human` |
| 3 | `name_self_declaration` | `name` + alternatives | 名称比对通过 | 驳回则试备选；仍失败 → `name_failed` |
| 4 | `select_authority` | `registration` | 进入设立信息填报 | 选项不匹配 → `need_human` |
| 5 | `fill_establishment` | company/investors/personnel/address | 各页保存成功 | 校验弹窗文案写入 `reason` |
| 6 | `choose_process` | `preferredProcess`、住所类型 | 确认进入电子化路径 | 被判线下 → `offline_required` |
| 7 | `fill_addons` | seals/tax/社保等 | 勾选的配套项填完 | 未勾选则跳过子步 |
| 8 | `submit_for_esign` | — | 出现待电子签名/提交成功文案 | 否则 `failed` / `need_human` |

### 9.3 扫码登录细节

1. Worker 打开从 yct 跳转的一网通办登录页。  
2. 定位二维码区域并截图 → API 提供给前端。  
3. **二维码过期**：定时重新截图，或识别失效文案后点击刷新。  
4. **登录成功检测**（多信号，避免误判）：离开登录 URL、出现用户信息/头像、特定 Cookie 组合等。  
5. 登录成功后 **同一 Context** 继续后续 Playbook。  
6. 若偶发滑块：可调用 `破盾工具` 或直接 `need_human`（MVP 可后者）。

**禁止：** 将政务 Cookie 下发到浏览器前端再回传。

### 9.4 住所与办理方式细节

```text
填完住所后：
  if 页面自动进入全程电子化:
      跳过人工选择，继续
  else if 用户 preferredProcess == full_electronic:
      尝试选择「无纸全程电子化登记」
      if 系统不允许:
          → offline_required + 截图
  else:
      → offline_required 或 need_human（MVP 不主动走线下代填）
```

### 9.5 结果解析优先级

1. 约定选择器上的成功/失败文案  
2. URL / 办件列表状态  
3. 仍不确定 → `need_human` + 全页截图

## 10. API 框架（最小契约）

| 方法 | 路径 | 说明 |
|------|------|------|
| `POST` | `/api/cases` | 创建办件，返回 `caseId` |
| `GET` | `/api/cases/:id` | 办件状态、result、artifact 链接 |
| `PATCH` | `/api/cases/:id/payload` | 更新向导数据（可带 `wizardStep`） |
| `POST` | `/api/cases/:id/validate` | 全量或指定步校验 |
| `POST` | `/api/cases/:id/start` | 开始自动化（需 `ready_to_submit`） |
| `POST` | `/api/cases/:id/resume-name` | 名称失败修改后继续核名 |
| `GET` | `/api/cases/:id/qr.png` | 当前登录二维码图 |
| `GET` | `/api/cases/:id/screenshots/:file` | 留痕图 |
| `POST` | `/api/cases/:id/files` | 上传附件，返回 `fileId` |
| `POST` | `/api/cases/:id/cancel` | 取消并关闭浏览器 |
| `GET` | `/api/health` | 健康检查（含 worker 是否空闲） |

### 10.1 `POST /start` 逻辑

```text
if status not in (ready_to_submit, name_failed 的特殊恢复路径):
    拒绝
if worker 忙（全局单任务）:
    拒绝或排队（MVP 直接拒绝并提示稍后再试）
创建 BrowserContext
状态 → awaiting_qr_login
异步执行 Playbook 链
```

### 10.2 前端轮询

- `start` 之后每 2～3 秒 `GET /cases/:id`。  
- `status === awaiting_qr_login` 时展示 `qrImageUrl`（可带 cache-bust 参数防缓存）。  
- 终态停止轮询。

## 11. 安全、合规与留痕

| 项 | 要求 |
|----|------|
| 身份 | 客户本人扫码、本人（及相关人员）签名；本系统为辅助填报 |
| 数据 | 证件与办件数据仅服务端存储；传输 HTTPS |
| 会话 | Cookie 仅存在于服务器 BrowserContext；案结即毁 |
| 审计 | caseId、状态变迁时间、关键截图路径可查 |
| 告知 | 确认页明示：将代为在官方页面填报已填写信息；法律后果由申请人承担 |
| 风控 | 不承诺绕过一切验证码；异常走 `need_human` |

## 12. 部署与运行框架

### 12.1 单机组成

```text
ECS
 ├─ web          静态或 SSR
 ├─ api          业务 API
 ├─ worker       Playwright + Chromium
 └─ volume       uploads / screenshots / db
```

### 12.2 运维要点

- Chromium 依赖、中文字体需在镜像中装全。  
- 安全组仅暴露 80/443（及 SSH）；Worker 不对外。  
- 无并发：API 层维护 `workerBusy` 锁即可。  
- 磁盘：截图与证件定期归档或清理策略需在上线前定。

### 12.3 研发工具 vs 生产

| 场景 | 工具 |
|------|------|
| 探 DOM、录步骤、调选择器 | Cursor + Chrome / 人工 DevTools |
| 生产执行客户单 | 仅 Playwright Worker |
| 滑块实验 | `破盾工具` 独立模块，按需接入 |

## 15. 验收标准（MVP Done）

1. 用户仅通过本系统分步向导完成信息采集与确认。  
2. 扫码在本系统进度页完成，登录态不经过「业务域 OAuth 回调」。  
3. 同一办件可从登录自动走到 **待电子签名**（名称可经修改/备选后通过）。  
4. **集中登记地**与**普通住所**两条路径均有至少 1 次真机验证；普通住所含证明上传。  
5. 若系统强制线下，状态为 `offline_required`，不出现假的 `awaiting_esign`。  
6. 成功返回可读提示 + 尽可能返回名称与办件号；失败必有 `reason` + 截图。  
7. 办件结束后 BrowserContext 关闭，无跨案 Cookie 复用。

## 16. 风险清单

| 风险 | 影响 | 缓解 |
|------|------|------|
| yct / 一网通办改版 | 选择器失效 | Playbook 版本化；失败截图；快速热更新配置 |
| 二维码过期、登录态掉线 | 流程中断 | 自动刷新二维码；步骤前检测登录，掉线回扫码 |
| 住所分支复杂 | 材料与办理方式多样 | 字段显式化；不通则 `offline_required` |
| 名称多次失败 | 体验差 | 备选名 + 只回名称步 |
| 电子签名人数多 | 用户以为已办结 | 待签名页写清应签角色与入口 |
| 验证码/风控 | 自动化卡住 | `need_human`；滑块模块可选接入 |
| 合规质疑 | 业务风险 | 本人登录本人签；留痕；确认页告知 |

## 17. 关键设计决策汇总

| 决策 | 结论 |
|------|------|
| 登录态放哪 | 服务器 Playwright Context，前端只看二维码图与状态 |
| 收集 UI | 分步表单向导，不是开放对话 |
| 住所 | 不唯一，向导与 Playbook 双分支 |
| 自动化终点 | 提交待签名，不代签 |
| 并发 | 单 Worker 单任务 |
| 账号 | 每客户自己扫码，不共用 |
| 官方 API | 无；仅浏览器自动化 + 统一业务状态契约 |
