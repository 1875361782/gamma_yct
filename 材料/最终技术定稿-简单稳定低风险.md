## 1. 你刚确认的两点

| # | 决策 |
|---|------|
| 1 | **测试止于提交前**（不点最终「提交」、不进入待电子签名） |
| 2 | **最简单、最稳定**；**尽量降低法律风险** |

由此直接推出执行层与产品边界（见下）。

---

## 2. 最终技术选型（一句话）

> **业务 Web 收集 + 扫码回站；Windows 云主机用 Playwright 填表并「暂存/保存到提交前」；Cursor / Chrome MCP 只用于研发探页，不进生产主路径；最终提交与电子签名由用户在官方站点本人完成。**

| 层级 | 选定 | 不选（及原因） |
|------|------|----------------|
| 用户可见 | 业务 Web（向导 + 二维码 + 进度） | 远程桌面给用户（暴露后台、体验差） |
| 填报引擎 | **Playwright 脚本 / Playbook** | Cursor Agent / Computer Use 主跑（不稳定、难审计、成本高） |
| 探路工具 | Cursor + Chrome MCP（人工/研发） | 不作为周 5 单生产运行时 |
| 自动化终点（测试+建议生产） | **提交按钮之前**（已填完并尽量「暂存」） | 自动点提交、自动签名 |
| 提交与签名 | **用户本人在 yct / 随申办完成** | 系统代点提交、代签 |
| 验证码 | 能扫码则扫码；滑块异常 → 暂停转值守 | 不以「破盾」为核心卖点 |
| 并发 | 单任务 | 多开 |

---

## 3. 为什么这样最稳、法律风险相对最低

### 3.1 稳定性

- Playwright：步骤可回归、失败可复现、不依赖每单大模型发挥。  
- 周约 5 单：单机单任务足够。  
- 状态机与二维码回传仍用原自助架构，只是执行器换成脚本。

### 3.2 法律 / 合规取向（降低风险，非律师意见）

| 做法 | 风险取向 |
|------|----------|
| 用户本人扫码登录 | 身份行为归用户，避免「借用/共用账号」 |
| 系统只根据用户已确认信息填表，并 **暂存** | 更接近「填写辅助」，而非擅自向机关递交申请 |
| **最终提交、电子签名由用户在官方页面完成** | 意思表示（申请/签名）留在用户侧 |
| 业务站显著告知与勾选同意 | 降低「未告知代操作」争议 |
| 不做验证码破解承诺、不做绕过风控宣传 | 降低不当技术使用风险 |
| 全流程截图留痕、可审计 | 便于客诉与内部合规 |
| 不宣称官方合作、不伪造政务页面 | 基础红线 |

**说明：** 即使不代提交，协助填报政务事项仍可能涉及地方代办/广告规范；若对外收费代办，需自行确认是否具备相应资质。本文只给工程上更稳妥的边界，**不构成法律意见**。

### 3.3 与「测到提交前」一致的产品终点

建议 **测试与一期生产采用同一终点**，避免测试一套、上线又自动提交：

```text
自动化成功终态：ready_for_user_submit（已填完，停在提交前 / 已暂存）
用户下一步：用同一账号在官方站打开草稿 → 核对 → 本人提交 → 本人电子签名
```

若 yct 草稿与账号绑定，用户手机登录同一账号通常可继续办理（以实现时页面为准；联调时验证「暂存后换端可见」）。

若暂存后换端不可见：备选是用户在业务站点「我已核对，授权打开提交页」后，**仅在用户二次确认下**由 Playwright 点一次提交——法律与产品风险高于「纯暂存」，一期不默认开启。

## 4. 目标用户流程（定稿）

```text
1. Web 分步填写并上传材料 → 校验 → 用户勾选「授权在官方页面填入我确认的信息（不含代为提交/签名）」
2. 开始办理 → 进度页展示二维码（云主机 Chrome 截图回传）
3. 用户扫码登录
4. 后台 Playwright：核名 → 选机关 → 填设立与配套 → 上传附件 → 暂存
5. 状态变为 ready_for_user_submit；展示截图摘要 + 操作指引
6. 用户自行在上海企业登记在线核对并提交、完成电子签名
7. （二期可选）进度查询回传办件状态
```

测试阶段：第 4 步做到「提交按钮可见但未点击」或「暂存成功」即停，写测试报告。

## 5. 系统架构（极简）

```text
[用户浏览器] 业务 Web
       │
[业务 API] Case / 文件 / 状态 / qr.png
       │
[Windows 云主机]
  · 常驻桌面会话 + Chrome/Chromium（Playwright 驱动）
  · Worker：按 Playbook 执行，单任务锁
  · 目录：cases/{id}/payload、uploads、screenshots、qr.png
  · 运营 RDP：仅 need_human 时介入
       │
[yct / 一网通办]
```

**不部署：** 生产路径上的 Cursor SDK、Computer Use 主循环、给客户的远程桌面。

**可保留：** 研发用 Cursor + Chrome MCP 录选择器、改 Playbook。

## 6. 状态机（相对前稿的调整）

| 状态 | 含义 |
|------|------|
| `draft` / `ready_to_submit` | 向导中 / 校验通过待开始 |
| `awaiting_qr_login` | 已出码，等用户扫 |
| `logged_in` … `filling_*` | 填报中 |
| **`ready_for_user_submit`** | **一期成功终态：已填完/已暂存，未代提交** |
| `name_failed` / `failed` / `need_human` / `offline_required` / `cancelled` | 同前 |

**不再把 `awaiting_esign` 作为一期自动化成功终态。**  
（用户本人提交后的待签名，可作为二期「进度查询」观察到的状态，而非我方自动点出来的状态。）

## 7. 需求清单（按最终选型）

### 7.1 工程 P0

1. Windows 云主机：防休眠、常驻可跑浏览器的会话  
2. Node 或 Python + Playwright + 中文字体依赖  
3. 业务 Web：分步向导 + 进度 + 二维码展示 + **授权文案勾选**  
4. 业务 API：Case、校验、start、qr.png、状态、截图  
5. Playbook：登录检测、核名、填表、上传、暂存；**禁止最终提交步骤**（配置开关默认关）  
6. 单任务锁 + 案结清 Cookie  
7. 运营 RDP 兜底  

### 7.2 材料 P0（真机前）

1. 开办样例字段表（可打码）  
2. 测试证件图  
3. 能登录 yct 的实名账号（扫码人）  
4. 确认：暂存后能否在手机端同账号继续（联调项）  

### 7.3 明确不做（一期）

- 自动点「提交」  
- 自动电子签名  
- 生产 Computer Use / Cursor 跑单  
- 破盾作为必保能力对外承诺  
- 多账号并发  

---

## 8. 测试验收（与「提交前」对齐）

测试通过 = 同时满足：

1. 用户仅通过 Web 完成填写与扫码。  
2. 后台自动完成核名与信息填入，**未点击最终提交**。  
3. 有清晰截图证明停在提交前或暂存成功。  
4. 名称失败、缺材料、`need_human` 行为正确。  
5. 案结会话清理完成。  

**不要求**测试阶段出现「待电子签名」。

## 9. 实施顺序（简化后）

| 阶段 | 内容 |
|------|------|
| W1 | Web/API/状态机 dry_run；Windows 上 Playwright 打开 yct 登录页并截二维码回 API |
| W2 | 扫码登录成功检测 + 核名 Playbook |
| W3 | 设立信息填报 + 附件 + 暂存；停在提交前；有样例后真机测 |
| W4 | 失败分支、同意书文案、值守流程、测试报告 |
| 之后 | 小流量生产（仍不代提交）；二期再评估「进度查询」 |

## 10. 一句话给业务/老板

**我们帮用户在官方页面把表填好并保存到提交前；登录、核对、提交、签名都由用户本人完成。技术用 Playwright 固定脚本，简单稳定；不做代提交、代签名，从产品边界上压低法律风险。**
